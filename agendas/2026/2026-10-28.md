## Abstracts

### Designing Language Specifications for Static Reasoning: Lessons from IRIDIUM

Programming language specifications are primarily written to define observable behaviour,
while implementations are designed for efficient execution. Our experience building IRIDIUM,
a static optimization framework for JavaScript, suggests that static analysis requires a third perspective:
what we call an _analysis-oriented semantics_.
Contrary to common intuition, the greatest obstacle to analyzing JavaScript is not dynamic typing,
but the loss of semantic structure between the language specification and production execution environments.

ECMAScript defines program behaviour through a rich collection of Abstract Operations, yet production engines
ultimately lower these operations into implementation-specific execution representations that compose many semantic
steps into a small number of generic operations. This semantic composition is desirable for execution,
but it obscures precisely the information that static analyses reason about. Once semantic structure has been collapsed,
analyses are forced to reconstruct it from implementation artefacts, often imperfectly. Conversely, an intermediate
representation that follows the specification too literally becomes difficult to lower efficiently onto existing runtimes.
Our experience suggests that analysis-oriented representations should instead preserve semantic structure that survives
across implementations while remaining expressible on diverse execution engines.

Building IRIDIUM led us to several observations that may be useful for language specification authors. First,
as the language evolves, preserving _functional completeness_ under desugaring is highly desirable, ensuring
that new syntactic features can be faithfully reduced to existing specification primitives. Syntactic conveniences
such as optional chaining (`a.b?.()`) cannot, in general, be desugared into existing constructs without introducing
subtle semantic differences, such as duplicate property evaluations or unexpected interactions with non-standard prototypes.
Guaranteeing sound desugaring paths helps preserve the long-term durability and usability of static analysis IRs.
Second, specifications can explicitly identify semantic obligations that are intended to be discharged either statically
or dynamically. Operations such as [`ToNumeric`](https://262.ecma-international.org/#sec-tonumeric),
[`RequireObjectCoercible`](https://262.ecma-international.org/#sec-requireobjectcoercible), bounds checks,
or prototype-cycle validation are semantically mandatory, but often become vacuous once an analyzer has established stronger invariants.
Rather than viewing these operations solely as runtime behaviour, specifications could designate them as optimization interfaces:
semantic obligations whose satisfaction may be established ahead of execution. This provides analyzers and implementations with
a shared vocabulary for optimization while preserving identical observable behaviour.

More broadly, our experience suggests that language specifications would benefit from distinguishing between semantics required
to define observable behaviour and semantic structure intended to support reasoning. Doing so neither restricts expressiveness nor prescribes
implementation strategy. Instead, it provides a stable interface between specifications, implementations, and analysis tools,
reducing the cost of optimization and verification while improving the long-term evolution of dynamic language ecosystems.
IRIDIUM taught us that many of the hardest problems in static analysis arise not from JavaScript's dynamic nature,
but from the absence of this interface.
